# 食刻 · 产品路线图

> 用途：下次讨论「还能加什么功能」时，先读这份文档，按这里的优先级继续。
> 最后更新：2026-11-03
> 当前版本：v1.0（微信小程序 + Web + Node API）

## 判断原则

1. **先降低记录成本，再谈更多 AI。** 用户不愿意每天记录，再强的识别也没有价值。
2. **先让目标可信，再做社交和付费。** 热量数字必须和用户的身体数据、目标有关。
3. **准确率不够时，先给用户纠错能力，而不是继续堆模型。**
4. 每加一个功能，必须能回答：它让用户**更容易记录**、**更相信数字**，还是**更愿意回来**？

## 优先级定义

| 级别 | 含义 |
|---|---|
| P0 | 下一批就做，直接影响核心闭环或留存 |
| P1 | 核心功能稳定后做，明显提升体验 |
| P2 | 有明确价值，但依赖前置能力或运营配置 |
| P3 | 差异化探索，等留存验证后再做 |

## 已完成

### 身体数据 + 自动计算目标（P0，已完成）

- 目标页填写：性别、年龄、身高、体重、活动量
- 服务端按 Mifflin-St Jeor 计算 BMR，乘活动系数得到 TDEE
- 减脂 / 维持 / 增肌自动生成热量、蛋白质、碳水、脂肪、纤维
- 手动修改目标后切换为手动模式
- 旧数据库自动迁移，旧用户目标保持不变
- 提交：`c930561 feat: 根据身体数据自动计算每日目标`

### 常用餐 / 复制昨天（P0，已完成）

- 日记里每一餐都能「存为常用餐」，同名同餐次重复保存会更新，不会产生重复模板
- 日记里每一餐都能「再来一份」，直接复制到当前查看的日期
- 首页「一键再吃」：常用餐一键记录；昨天吃过的餐可一键复制到今天
- 识别结果页可勾选「保存为常用餐」，保存这一餐时顺带建立模板
- 食物搜索空关键词时显示最近吃过的 20 种食物
- 复制和常用餐都由服务端重新计算营养，不信任存下来的总量

## P0 · 下一批

### 1. 剩饭比例

**问题**：AI 识别的是「盘子里有什么」，但用户实际没吃完。

**做法**：

- 在确认份量页加「这盘吃了几成？」：100% / 75% / 50% / 25%
- 所有食材按比例折算
- 保留单项微调能力

**验收**：

- 选 50% 后，总热量和宏量准确减半
- 不影响原有的单项克数编辑

**成本**：低
**价值**：高（直接提升热量准确度）

### 2. 份量参照

**问题**：大多数用户不知道 100g 米饭、100g 肉是多少。

**做法**：

- 在克数编辑区显示视觉参照：
  - 一个拳头 ≈ 100g 米饭
  - 一个掌心 ≈ 100g 肉
  - 一勺油 ≈ 10g
- 每种食物优先显示自己的 `portionHint`

**验收**：

- 用户不看营养表也能选出一个合理克数
- 不增加页面层级

**成本**：低
**价值**：高

## P1 · 核心稳定后

### 3. 体重趋势

- 每周记录一次体重
- 折线趋势 + 周平均
- 体重变化后自动重算目标
- 只呈现趋势，不评价胖瘦

**成本**：低
**价值**：高

### 4. 识别纠错 / 自定义食物

- 每个识别项可以「换一种食物」
- 支持自定义食物和每 100g 营养值
- 记住用户常吃的别名，下次优先匹配
- 低置信度时主动提示确认

**成本**：中
**价值**：高（建立个人食物库，越用越准）

### 5. 周报 + 连续记录

- 7 天热量 / 蛋白质趋势
- 达标天数、餐盘质量趋势
- 连续记录天数
- 每周一条可执行总结
- 分享卡片（默认不暴露体重和照片）

**成本**：中
**价值**：高（留存和分享）

## P2 · 有前置条件

### 6. 微信订阅消息提醒

- 午餐 / 晚餐记录提醒
- 周报生成提醒
- 连续记录中断提醒

**前置条件**：

- 微信公众平台申请订阅消息模板
- 用户主动授权，不能静默推送
- 服务端定时任务
- 控制频率，避免打扰

**成本**：中
**价值**：中

### 7. 营养标签 OCR

- 拍包装背面的营养成分表
- 识别每 100g 的热量、蛋白质、碳水、脂肪
- 用户输入吃了多少克

**为什么排在条码前面**：

- 中国商品条码数据库覆盖差，自建成本高
- 营养标签 OCR 对零食、饮料、代餐更直接

**成本**：中
**价值**：高

## P3 · 差异化探索

### 8. 餐厅菜单识别

拍菜单 → 识别菜品 → 选菜 → 按标准份量估算。

份量误差较大，适合作为尝鲜功能，不作为核心准确度承诺。

### 9. AI 饮食教练

基于当天剩余热量和宏量回答「晚上还能吃什么」。

**限制**：

- 只在食物库内推荐
- 不给医疗建议
- 每天限次数，控制成本

### 10. 家庭 / 社交

- 一个微信账号管理多个家庭成员
- 朋友一起打卡、周挑战

需要改数据模型和隐私设计，等留存验证后再做。

## 暂不做

| 功能 | 原因 |
|---|---|
| 社交动态、排行榜、积分商城 | 核心记录习惯还没验证，容易分散注意力 |
| 复杂食谱计划、买菜清单 | 依赖周计划和菜谱数据，范围过大 |
| 睡眠、喝水、运动全量记录 | 会稀释「食物记录」定位 |
| 微信步数接入 | `wx.getWeRunData` 需要 `session_key`，当前登录流程已丢弃，改造成本高 |
| 多语言 | 目标用户以中文为主 |
| 会员付费 | 先验证留存，再设计付费点 |

---

## 推荐执行顺序

1. 剩饭比例 + 份量参照
2. 周报 + 连续记录
3. 体重趋势
4. 识别纠错 / 自定义食物
5. 订阅消息
6. 营养标签 OCR
7. 餐厅菜单 / AI 教练 / 家庭社交

## 技术约束备忘

- 小程序营养/建议/身体数据计算与 `shared/` 重复，改动时必须两边同步，并跑 `server/tests/miniprogram.test.ts` 的 parity 测试。
- SQLite 单实例，部署时需要持久化 `/app/data`。
- 新增 profile 字段要通过 `server/store.ts` 的 `addColumnIfMissing` 迁移。
- 微信订阅消息必须用户主动授权，不能当作普通 push。
- 分享卡片默认不包含体重、照片等敏感信息。
- 上线前仍需处理：`ALLOW_DEMO=false`、隐私文案与图片存储一致、删除餐次时清理图片文件。
