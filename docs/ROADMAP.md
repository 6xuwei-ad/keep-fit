# 食刻 · 产品路线图

> 用途：下次讨论「还能加什么功能」时，先读这份文档，按这里的优先级继续。
> 最后更新：2026-11-05
> 当前版本：v2.0（微信原生小程序 + Node API）

## 判断原则

1. **先降低记录成本，再谈更多 AI。** 用户不愿意每天记录，再强的识别也没有价值。
2. **先让目标可信，再做社交和付费。** 热量数字必须和用户的身体数据、目标有关。
3. **准确率不够时，先给用户纠错能力，而不是继续堆模型。**
4. 每加一个功能，必须能回答：它让用户**更容易记录**、**更相信数字**，还是**更愿意回来**？

## 优先级定义

| 级别 | 含义 |
|---|---|
| P0 | 下一批就做，直接影响核心闭环或留存 |
| P1 | 核心功能稳定后做，明显提升体验 |
| P2 | 有明确价值，但依赖前置能力或运营配置 |
| P3 | 差异化探索，等留存验证后再做 |

## 已完成

### 身体数据 + 自动计算目标（P0，已完成）

- 目标页填写：性别、年龄、身高、体重、活动量
- 服务端按 Mifflin-St Jeor 计算 BMR，乘活动系数得到 TDEE
- 减脂 / 维持 / 增肌自动生成热量、蛋白质、碳水、脂肪、纤维
- 手动修改目标后切换为手动模式
- 旧数据库自动迁移，旧用户目标保持不变
- 提交：`c930561 feat: 根据身体数据自动计算每日目标`

### 常用餐 / 复制昨天（P0，已完成）

- 日记里每一餐都能「存为常用餐」，同名同餐次重复保存会更新，不会产生重复模板
- 日记里每一餐都能「再来一份」，直接复制到当前查看的日期
- 首页「一键再吃」：常用餐一键记录；昨天吃过的餐可一键复制到今天
- 识别结果页可勾选「保存为常用餐」，保存这一餐时顺带建立模板
- 食物搜索空关键词时显示最近吃过的 20 种食物
- 复制和常用餐都由服务端重新计算营养，不信任存下来的总量

### 剩饭比例 + 份量参照（P0，已完成）

- 确认份量页新增「这盘实际吃了多少」：100% / 75% / 50% / 25%
- 整盘食材按比例折算，之后单独改克数也不会漂移（内部保留 100% 基准克数）
- 每种食物最多显示 2 个可点击的份量参照，如「一掌心 ≈ 100g」
- 参照优先使用食物库的份量提示，没有时按品类兜底（主食拳头、蛋白掌心、油一勺）

### 体重趋势（P1，已完成）

- 独立的「体重趋势」页，从首页和目标页都能进入
- 每周记录一次，同一天重复记录视为修正；不能记录未来日期
- 折线图按自然周（周一到周日）画平均值，最多 12 周；同时显示本周平均
- 只有存在 28 天前的记录时，才显示「近 4 周变化」，避免把短期波动说成长期趋势
- 新体重自动同步到档案；目标页改体重也会写入今天的记录，避免两个数字
- 自动目标模式会按新体重重算热量与三大营养素，手动模式不改目标
- 删除记录后趋势、周平均和档案体重会一起回退
- 文案只描述数字，不评价胖瘦

### 识别纠错 / 自定义食物（P1，已完成）

- 每个识别项新增「换一种」：替换名称、`foodId`、每 100g 营养值和份量参照，保留当前克数
- 单项置信度低于 60% 时标红，并在顶部提示有几项需要核对
- 自定义食物库：新建、编辑、删除；填写每 100g 营养值和常用份量
- 搜索结果里自定义食物排在内置库前面，带「我的」标记，同名内置项不重复出现
- 替换时记住模型原来的叫法；下次识别命中别名，直接使用用户确认过的食物
- 服务端保存时仍然重新计算营养；自定义食物保留 `custom` 来源和 `foodId`

## P1 · 核心稳定后

### 1. 周报 + 连续记录

- 7 天热量 / 蛋白质趋势
- 达标天数、餐盘质量趋势
- 连续记录天数
- 每周一条可执行总结
- 分享卡片（默认不暴露体重和照片）

**成本**：中
**价值**：高（留存和分享）

---

## P2 · 有前置条件

### 2. 微信订阅消息提醒

- 午餐 / 晚餐记录提醒
- 周报生成提醒
- 连续记录中断提醒

**前置条件**：

- 微信公众平台申请订阅消息模板
- 用户主动授权，不能静默推送
- 服务端定时任务
- 控制频率，避免打扰

**成本**：中
**价值**：中

### 3. 营养标签 OCR

- 拍包装背面的营养成分表
- 识别每 100g 的热量、蛋白质、碳水、脂肪
- 用户输入吃了多少克

**为什么排在条码前面**：

- 中国商品条码数据库覆盖差，自建成本高
- 营养标签 OCR 对零食、饮料、代餐更直接

**成本**：中
**价值**：高

---

## P3 · 差异化探索

### 4. 餐厅菜单识别

拍菜单 → 识别菜品 → 选菜 → 按标准份量估算。

份量误差较大，适合作为尝鲜功能，不作为核心准确度承诺。

### 5. AI 饮食教练

基于当天剩余热量和宏量回答「晚上还能吃什么」。

**限制**：

- 只在食物库内推荐
- 不给医疗建议
- 每天限次数，控制成本

### 6. 家庭 / 社交

- 一个微信账号管理多个家庭成员
- 朋友一起打卡、周挑战

需要改数据模型和隐私设计，等留存验证后再做。

## 暂不做

| 功能 | 原因 |
|---|---|
| 社交动态、排行榜、积分商城 | 核心记录习惯还没验证，容易分散注意力 |
| 复杂食谱计划、买菜清单 | 依赖周计划和菜谱数据，范围过大 |
| 睡眠、喝水、运动全量记录 | 会稀释「食物记录」定位 |
| 微信步数接入 | `wx.getWeRunData` 需要 `session_key`，当前登录流程已丢弃，改造成本高 |
| 多语言 | 目标用户以中文为主 |
| 会员付费 | 先验证留存，再设计付费点 |

---

## 推荐执行顺序

1. 周报 + 连续记录
2. 订阅消息
3. 营养标签 OCR
4. 餐厅菜单 / AI 教练 / 家庭社交

## 技术约束备忘

- 小程序营养/建议/身体数据计算与 `shared/` 重复，改动时必须两边同步，并跑 `server/tests/miniprogram.test.ts` 的 parity 测试。
- SQLite 单实例，部署时需要持久化 `/app/data`。
- 新增 profile 字段要通过 `server/store.ts` 的 `addColumnIfMissing` 迁移。
- 自定义食物与别名都按 `device_id` 隔离；别名保存的是食物快照，自定义食物删除后别名仍可用。
- 微信订阅消息必须用户主动授权，不能当作普通 push。
- 分享卡片默认不包含体重、照片等敏感信息。
- 上线前仍需处理：`ALLOW_DEMO=false`、隐私文案与图片存储一致、删除餐次时清理图片文件。
